**Plan: Adapter Registry + Selectable Handlers (Manual + Generated)**

- **Goal & Constraints**
  - Worker code must stay isolated from main code (no main dependencies).
  - Codegen is optional; everything must be possible to implement by hand.
  - Registry should be discoverable from dependencies, but also allow manual “manifest” files.
  - Users can exclude unwanted dependency registries (to keep worker.js slim).

---

### 1) Define the Registry Contract (manual or generated)
- **Introduce a manifest file name convention**  
  - Use a **stable, hand-authorable filename** in adapter packages (per your request):  
    `lib/src/locorda_adapter_registry.manifest.dart`
  - This file can be either:
    - manually written by a package author, or
    - generated by a builder (optional).
- **Registry contents** should describe:
  - `id` / `key` (matches existing handler IDs),
  - handler “kind” (`storage` or `remote`),
  - worker handler factory.
- Multiple instances of the same handler type are supported (different IDs).
  All configuration comes from main at runtime — no defaults in the manifest.
- **No main-side class references** in worker registry.

---

### 2) Add a registry aggregator in the app package (builder)
- **Builder in app package** scans for registry manifests across all packages:
  - `BuildStep.findAssets` is scoped to the **current package only**, so it
    cannot discover registries in dependencies.
  - Use `buildStep.packageConfig` to list all packages, then probe each package
    explicitly with `buildStep.canRead(AssetId(pkg, 'lib/src/locorda_adapter_registry.manifest.dart'))`.
  - For each readable asset, load and merge it into the aggregated registry.
- **Configurable exclusions** (in build.yaml):
  - Allow `exclude_packages` list, e.g.:
    ```yaml
    targets:
      $default:
        builders:
          locorda_dev|locorda_registry_aggregator:
            options:
              exclude_packages:
                - locorda_gdrive
                - dropbox_for_locorda
    ```
  - Filter out manifests whose `AssetId.package` is excluded.

---

### 3) Runtime Selection: Use IDs + WorkerParams
- **Keep existing handler contracts**:
  - Storage/Remote handlers remain in:
    - storage_main_handler.dart
    - storage_worker_handler.dart
    - remote_main_handler.dart
    - remote_worker_handler.dart
- **WorkerParams becomes the runtime registry “selector”**:
  - Change `WorkerParams.storage` from single to **list** to allow multiple storage candidates.
  - Add a way to **select active ones** based on main-side ids.
  - Selection happens before `toEngineParams` is called in
    worker_params_to_engine_params.dart.

---

### 4) Main/Worker Coordination: IDs + config handoff
- **Main side provides:**
  - chosen storage id + config
  - chosen remote ids + configs
- **Worker side uses registry** to instantiate matching handlers, ignoring others.
- This mirrors existing remote `id` matching logic (already used by `RemoteMainHandler.id` and `RemoteWorkerHandler.id`).

---

### 5) Manual Override Path (No Codegen Required)
- Provide a documented manual setup path:
  - User writes their own `lib/src/locorda_adapter_registry.manifest.dart`.
  - User opts out of generator in build.yaml or doesn’t add locorda_dev.
  - User writes `initLocorda` and worker.dart manually.
- The builder should **only aggregate** manifests if enabled.

---

### 6) Update Example Apps to Validate Flow
- Use:
  - main.dart
  - worker.dart
- Demonstrate:
  - local dir variants declared in manifest
  - active selection in `initLocorda(...)`
  - worker auto-instantiating only selected handlers

---

### 7) Tests
- Unit tests for:
  - registry aggregation + exclusion filtering
  - selection logic (only active ids are used)
  - worker/main mismatch detection for ids
- Make sure it covers the “manual manifest only” path.
